# 06 — The iMessage Bridge (drafted 2026-08-01)

**Thesis:** the best interface for a personal AI is the one already on every
device you own. Texting. A second iCloud account signs into Messages on the
Mac — it is a **mouthpiece, not a worker**: it owns no data, does no work, and
exists only so the human has a contact to text. The Mac does everything, as
the human's own account, through the governed tools. The market's iMessage
assistants (Poke, Arlo, Sidekicks, Olly) are cloud services on Apple's
business-messaging rails: your requests and data flow through their servers,
and none of them can touch Apple-native data at all — no API exists for it.
Only a Mac-side bridge can. That is the moat, and the responsibility.

## The three laws (set by the operator, 2026-08-01)

1. **Only the owner commands.** The bridge acts solely on messages whose
   sender handle is in the configured owner allowlist (the human's phone
   number and Apple ID handles). Verified from chat.db — Apple authenticates
   iMessage senders; this is a real boundary, not a heuristic.
2. **Everyone else is silence.** Messages from any other sender are ignored
   COMPLETELY — not fenced, not summarized, not answered, not surfaced to the
   model at all. A counter in the audit log is their only trace.
3. **The bridge is structurally blind to every other conversation.** The
   chat.db layer filters to the owner↔assistant thread at the SQL boundary.
   There are NO general Messages-reading tools in v1 — the creepiest surface
   stays untouched (docs/04's Q13 reasoning, upheld).

## The subtle threat, named

The dangerous message is not from a stranger — it is from the owner,
containing text the owner did not write: a forwarded email, a pasted scam, a
shared article. That content rides the instruction channel. The defense is
the layering that already exists: injected content can at most make the model
*ask* for an action; every consequential action still needs approval, and the
approval nonce is generated by the framework, verified by the framework, and
never enters model context — content cannot forge what it cannot see.

## Approvals by reply (the channel that retires the file-move)

Gated action → the bridge texts the owner: what wants to run, and
"reply `yes <nonce>` / `no <nonce>`" (nonce = 6 chars, per-request,
single-use, dead at deadline). The FRAMEWORK polls chat.db for a reply from
an allowlisted handle carrying the exact nonce — the model never relays the
decision. Timeout, wrong nonce, unknown sender: deny. This is the same trust
class as the folder channel (surface: Apple-authenticated infrastructure the
model cannot write to) with the UX of texting "yes 4f2a1c".

## Architecture (@honeycrisp/imessage)

- **chatdb.ts** — read-only SQLite on `~/Library/Messages/chat.db` (needs
  Full Disk Access). Incremental ROWID cursor; sender allowlist IN the SQL;
  is_from_me excluded from inbound. Ventura+ messages often carry text only
  in `attributedBody` (a typedstream blob) — best-effort decoder, and rows
  whose text cannot be decoded are DROPPED, never guessed.
- **send.ts** — AppleScript send via Messages. v1 exposes exactly one send
  path: **to the owner**. `message_send_owner` is write-safe (talking TO the
  human is always allowed — it is the review loop). No general send tool
  exists; messaging anyone else is not gated, it is absent.
- **approval.ts** — `ImessageApprovalChannel` (reply-to-approve above). Used
  by the bridge's own governed servers via the approval override; other MCP
  hosts keep their existing channels.
- **brain.ts** — the local agent loop, promoted from the Q28 field-test
  harness: Ollama chat with tools (arg-normalization shim included), driving
  the suite's tool sets in-process through `executeGoverned` — mail,
  reminders, notes, calendar, context, resolved via the module resolver like
  the remote gateway's mounts. Model configured in config.json; egress
  posture identical to the context layer's ModelProvider (local by default,
  declared if not).
- **bridge.ts** — the daemon: poll inbound (owner-only) → brain → reply via
  send-to-owner. Every inbound command, reply, ignored-sender count, and
  approval outcome is an audit row.
- **cli.ts** — `honeycrisp-imessage run | status | test`, launchd template.

## What must be true on the Mac (operator setup, one time)

1. A second Apple ID, signed into **Messages.app only** (Mac's system iCloud
   stays the owner's). Strong password + 2FA — if this account is hijacked,
   the thief can read what the assistant sends (so the assistant texts
   summaries and alerts, never full content) and can impersonate it socially;
   they still cannot command the bridge (law 1) or approve anything (nonce
   lives in chat.db conversation with allowlisted handles only).
2. Full Disk Access for the host process (chat.db).
3. Automation permission → Messages (sending).

## Milestones

- **M0 — testable core (no account needed):** chatdb reader + decoder +
  allowlist against a synthetic chat.db fixture; send builders with
  injection-safety tests; approval channel end-to-end against the fixture;
  bridge loop with injected fakes. All pure, all CI-able.
- **M1 — live on this Mac:** second account, FDA, real send, first
  text-in/text-out conversation; approval-by-reply live test.
- **M2 — the daily driver:** launchd, briefing highlights pushed as texts,
  wizard step, docs. Then the killer demo: "remind me Thursday" from a
  phone, approved by replying yes.
